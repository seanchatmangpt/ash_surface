# AshSurface conformance corpus

A language-neutral, versioned set of golden vectors so a new projection (Vue,
Expo, Kotlin, ...) can **self-certify against the Elixir implementation** instead of
copying a twin implementation and hoping it agrees.

```text
Ash -> Manifest -> AshSurface -> { JavaScript, Phoenix, Vue, Expo, Kotlin, ... }
                        |
                conformance/vectors/*.json   (generated by the real Elixir implementation)
```

The corpus is *generated, never hand-typed*: every `expected` value is produced by
the public Elixir modules (`AshSurface.Transport`, `CanonicalJSON`,
`from_manifest/2`, `IR.Codec`, `Event.from_receipt/2`, `Standing`, `Vocabulary`).
Ash resources/actions/policies stay authoritative; the corpus only records what the
implementation does today.

## Layout

| Path | What |
|---|---|
| `conformance/MANIFEST.json` | corpus version, law version, per-file `sha256`, vector counts, level counts. No clock, commit, or host data, so regeneration is byte-identical. |
| `conformance/vectors/<kind>.json` | one file per vector family (11 files, 547 vectors at 1.0.0). |
| `conformance/elixir/runner.exs` | the Elixir reference runner: one function per kind, driving the real implementation. |
| `conformance/js/reference.mjs` | JavaScript twins of the digest laws (canonical JSON, ETF term digest, receipt binding). Use or port these. |
| `conformance/js/replay.mjs` | the JavaScript replay engine (per-vector `PASS / FAIL / NOT_APPLICABLE / KNOWN_DIVERGENCE`). |
| `conformance/js/known_divergences.mjs` | pinned, asserted JS/Elixir disagreements. |
| `scripts/conformance_regen.exs` | regenerates the corpus. |
| `test/conformance/conformance_replay_test.exs` | Elixir replay: corpus == implementation. |
| `test/js/conformance_replay.test.mjs` | JS replay against `priv/static/ash_surface_runtime.mjs` (runs under `npm test`). |

## Vector format

Each `vectors/<kind>.json` is `{"corpusVersion", "kind", "vectors": [ ... ]}` with one
vector per line:

```json
{"id": "ts/d=h,c/a=h,c/p=h/f=none", "description": "...", "input": {...},
 "expected": {...}, "notes": "...", "level": "MUST"}
```

`input` and `expected` are plain JSON. Errors are normalized to
`{"error": {"kind": "<snake_case>", "detail": ...}}`: **`kind` is normative,
`detail` is diagnostic** (do not compare it across languages).

### Kinds

| kind | input -> expected |
|---|---|
| `transport_selection` | `{declared, available, preferred, actionId, profile?.transportFacts}` -> `{decision: {selected, reason, dimensions, frontier, declared, available, preferred, dispatchState, fallback, actionId}}` or `{error}`. Includes the exhaustive small space (declared sets x available orderings x preferred x 13 fact scenarios = 364 rows) and edge cases (empty available, duplicates, unknown/unadmitted transports, unknown dimension/class, ties, `medium`, dominated preference). |
| `transport_facts_admission` | `{profile}` -> `{facts}` or `{error}` (absent/null facts are "not delegated", never defaulted). |
| `canonical_json` | `{json: <text>}` -> `{canonical, sha256}` (key order by UTF-8 bytes, unicode, escapes, numbers, nesting). |
| `surface_contract_digest` | `{contract, generation?}` -> `{digest}` (`from_manifest/2` contract digest; `generation` lets Elixir rebuild the contract, tamper vectors have none). |
| `surface_contract_refusal` | `{generation}` -> `{error}` (profile / refusal-code admission at contract minting). |
| `receipt_digest` | `{payloadJson}` -> `{sha256}` (receipt hash law). |
| `receipt_binding` | `{receipt, irAction?}` -> `{event}` or `{refusal: {standing, reason, authorityBoundary}}` (digest binding, tamper cases, refusal ordering subject -> timestamp -> digest). |
| `refusal_vocabulary` | `{value}` -> `{refusalCode, standingValid, standingRefused}` (`REFUSED_` + non-empty reason). |
| `reconcile_status` | `{verdict}` -> `{admitted}` (only `COMPLETED`, `NOT_OBSERVED`, `STILL_UNKNOWN`; other keys pass through). |
| `ir_codec` | `{map}` -> `{ok: {canonicalMap, digest, roundTripsInput}}` or `{error}` (`false` leaves, nil honesty, forward tolerance, digest). |
| `transport_outcome` | `{phase: pre_dispatch\|post_dispatch, cause, declared, available, preferred}` -> `{dispatchState, fallbackAllowed, failureOutcome}` (post-dispatch failure -> `dispatched`, fallback closed, `UNKNOWN_AFTER_DISPATCH`; pre-dispatch -> `not_dispatched`, fallback open, no outcome). |

## How a new projection certifies

1. **Load** `MANIFEST.json`; verify each file's `sha256`; require `corpusVersion`'s major to
   be one you support.
2. **Replay** every vector of every kind you implement. For each vector you MUST report
   exactly one status: `PASS`, `NOT_APPLICABLE` (with a reason: your API cannot express
   the input), or `KNOWN_DIVERGENCE` (with your exact output pinned). Silent skips are
   non-conformance. `conformance/js/replay.mjs` is the model.
3. **Levels**:
   * `MUST` - required whenever the projection implements the capability and can
     express the input. Any `FAIL` blocks certification.
   * `MAY` - order-parametric rows (declared order `[phoenix_channel, http]`, or an
     `available` order different from `declared`). Required only if your API lets a
     caller state those orders; otherwise `NOT_APPLICABLE`.
   * `PENDING_DECISION` - the spec point is genuinely undecided (numeric lexical form:
     int vs float spelling, integers beyond 2^53, duplicate JSON keys). The Elixir
     result is recorded; you neither pass nor fail, but you MUST declare your behavior
     as a known divergence or match Elixir.
4. **Transport law is MUST**: selection before dispatch; a post-dispatch failure
   (rejection, deadline, abort) is `UNKNOWN_AFTER_DISPATCH` and the alternate
   transport is never invoked (the JS replay drives real adapters and counts calls).
5. Never report a projection ALIVE from this corpus alone: generated or rendered code
   needs an exact consumer execution receipt (AGENTS.md).

`NOT_APPLICABLE` is honest, not a pass: the JS replay currently declares 178 vectors NOT_APPLICABLE (162
transport-selection rows, 156 of them MAY, plus 16 others), each with a reason
(fixed declared order, no back-projection, no manifest minting, ...).

## Versioning

* `corpusVersion` (semver, `AshSurface.Conformance.Runner.corpus_version/0`):
  patch = new vectors/notes only; minor = new kind or new vectors that tighten a law;
  major = a changed `expected` for an existing vector id (a behavior change).
* `lawVersion` records `AshSurface.schema_version/0` at generation time.
* Vector ids are stable; never reuse an id for different input.
* Changing Elixir behavior means regenerating; the diff of `expected` is the
  reviewable record of the change, and the Elixir replay is RED until then.

## Regeneration

```sh
source /etc/profile.d/beam.sh
MIX_ENV=test mix run scripts/conformance_regen.exs   # MIX_ENV=test: fixtures use the test-support resource
mix test test/conformance                            # Elixir replay
node --test test/js/conformance_replay.test.mjs      # JS replay (also part of `npm test`)
```

Inputs are authored in the script; `expected` comes from the real implementation via the
runner. Output is deterministic (sorted-key canonical JSON, one vector per line, no
clocks): two runs are byte-identical. After a regeneration that changes JS behavior, run
the JS replay and update `known_divergences.mjs` only with a documented reason.

## Known divergences (1.0.0) - real cross-language findings

Pinned in `conformance/js/known_divergences.mjs` (each is asserted to still diverge):

1. **Refusal pattern and line terminators (MUST, 4 vectors `rv/multiline/*`).** JS
   `refusalCodeSchema` is `/^REFUSED_.+/` without the dotall flag, so a reason that
   *begins* with `\n`, `\r`, U+2028 or U+2029 is refused; Elixir
   (`Vocabulary.refusal_code?/1`: prefix + any non-empty rest) admits it. Fix either
   side: JS `/^REFUSED_[\s\S]+/`, or tighten Elixir to a token charset.
2. **Numeric lexical form (PENDING_DECISION, 10 vectors).** Elixir keeps the int/float
   distinction and Erlang float spelling (`1.0`, `1.0e5`, `-0.0`, exact bigints); JS
   `JSON.parse`/`JSON.stringify` cannot. Canonical JSON, contract digests (`2.0` vs `2`),
   receipt hashes and receipt binding all inherit it: a receipt whose value is `2.0` on the
   wire and was minted by JS over `2` is REFUSED_RECEIPT_DIGEST_MISMATCH in Elixir.
   `Idempotency.request_digest/2` already refuses floats for this reason; the same
   restriction (or a lexical canonical number rule) is needed for receipts and contracts.
3. **Shipped minting law is not corpus-conformant.** `canonicalStringify` in
   `test/js/consumer_e2e_runner.mjs` uses the default UTF-16 key sort and
   `JSON.stringify` escapes; it differs from `CanonicalJSON` for astral-vs-high-BMP key
   order and for control characters (`\u001f` vs `\u001F`). `conformance/js/reference.mjs`
   is conformant; the runner should adopt it. Pinned by a test, not a divergence entry.

## Gaps for the upstream owners (not changed by this corpus)

* The JS runtime exports no canonical-JSON / digest / receipt-hash helper, so every JS
  consumer re-implements them; export the `reference.mjs` laws from the runtime.
* Elixir has no public `AshSurface.digest/1` for a contract (the corpus uses
  `IR.Codec.digest/1`, the same canon, and asserts agreement with `from_manifest/2`).
* Elixir has no post-dispatch failure classifier; `failureOutcome` in `transport_outcome`
  is derived from `Transport.fallback_allowed?/1` + `Vocabulary.dispatch_outcomes/0`.
  A `Transport.classify_failure/2` would let the corpus record it directly.
